# Desktop Advanced Features

This document covers two advanced subsystems in the DeepSeek-Reasonix desktop application: the multi-tab system that enables concurrent project sessions, and the auto-updater that keeps the application current.

---

## Multi-Tab System

**Source:** `desktop/tabs.go`

### Overview

The desktop application supports multiple concurrent conversation tabs, each scoped to an independent workspace. Each tab owns its own controller — complete with a dedicated agent, session, tool registry, plugin host, memory, and permissions — so multiple projects and topics can be active simultaneously without interfering with one another. This design enables a developer to work on a backend service in one tab, a frontend project in another, and a global scratchpad in a third, all within a single application window.

### WorkspaceTab

The `WorkspaceTab` struct represents one open conversation tab:

| Field | Type | Description |
|---|---|---|
| `ID` | `string` | Stable random identifier (UUID-like). |
| `Scope` | `string` | `"project"` or `"global"`. |
| `WorkspaceRoot` | `string` | Project root directory (empty for global scope). |
| `TopicID` | `string` | Topic identifier within the project. |
| `TopicTitle` | `string` | Display title, auto-generated from the first user message. |
| `Ctrl` | `*control.Controller` | The tab's controller (nil while booting or on error). |
| `Label` | `string` | Model label shown in the tab badge. |
| `Ready` | `bool` | True once `boot.Build` completes successfully. |
| `StartupErr` | `string` | Build error message, surfaced to the frontend. |
| `model` | `string` | Active model reference (for metadata). |
| `effort` | `*string` | Optional reasoning effort override. |
| `mode` | `string` | `"normal"`, `"plan"`, or `"yolo"` (yolo is runtime-only). |
| `disabledMCP` | `map[string]ServerView` | MCP servers disabled for this tab. |
| `mcpOrder` | `[]string` | MCP server order for this tab. |

### Tab Scopes

Each tab operates in one of two scopes:

- **Project scope** (`"project"`): The tab is associated with a specific workspace root directory. All file operations, memory, and tool permissions are scoped to that directory. Multiple project-scoped tabs can reference the same workspace root with different topics.

- **Global scope** (`"global"`): The tab has no project root. Instead, it uses the Reasonix user configuration directory as its workspace root. This is useful for general-purpose conversations, configuration management, or tasks that don't belong to a specific project.

### Topics

Topics are conversation threads within a project. A project can have multiple topics, each with its own session history. Topics are auto-titled from the first user message using `topicTitleFromText`, which:

1. Trims whitespace and collapses multiple spaces.
2. Strips common punctuation (both Western and CJK).
3. Truncates to 18 runes, adding an ellipsis if needed.
4. Rejects the default title ("New Topic") to avoid confusion.

Topic titles can also be set manually or generated by the LLM after the first turn, with the source tracked as `topicTitleSourceAuto` to distinguish auto-generated titles from user-set ones.

### tabEventSink: Frontend Event Routing

`tabEventSink` wraps the parent `event.Sink` and prepends the tab's ID to every wire event. This allows the frontend to route events to the correct tab's reducer:

```go
type tabEventSink struct {
    tabID string
    app   *App
    ctx   context.Context
}
```

The `Emit` method:

1. Emits the event via `runtime.EventsEmit` with the tab ID attached, so the frontend can dispatch to the correct per-tab state.
2. Records `read_file` successes in the tab's telemetry (see below).
3. Schedules a tab snapshot after each `TurnDone` event for autosave.

When a tab is closed, its sink's `ctx` is set to `nil`, which makes `Emit` a no-op — preventing events from a shut-down controller from reaching the frontend.

### Per-Tab Autosave: scheduleTabSnapshot

Each tab has its own autosave loop that persists the session after each turn:

1. `scheduleTabSnapshot(tabID)` checks if the tab is already saving. If so, it sets `saveAgain = true` (coalescing multiple save requests). If not, it starts the save loop.

2. `tabSnapshotLoop(tab)` runs in a background goroutine:
   - Takes a snapshot via `ctrl.Snapshot()`.
   - Attempts to auto-title the topic from the session content.
   - If `saveAgain` was set during the save, loops again immediately (the "save/saveAgain" pattern ensures no save is lost).
   - Otherwise, marks the tab as not saving and exits.

This pattern ensures that rapid successive turns (e.g., the user submitting multiple messages quickly) don't queue up redundant saves while also guaranteeing that the final state is always persisted.

### Per-Tab Read Telemetry

Each tab tracks file reads for diagnostic and UX purposes via `readFileRecord`:

| Field | Type | Description |
|---|---|---|
| `Path` | `string` | The file path that was read. |
| `Turn` | `int` | The turn number when the read occurred. |
| `Time` | `int64` | Unix millisecond timestamp. |
| `Offset` | `int` | Line offset (if partial read). |
| `Limit` | `int` | Line limit (if partial read). |
| `Truncated` | `bool` | Whether the file was truncated. |

Records are collected when `read_file` tool results arrive via the event sink. The telemetry is persisted to `<session-path>.telemetry.json` after each read, ensuring that data survives even an unclean shutdown. When a tab resumes an existing session, previously saved telemetry is loaded back into memory.

### Tab Persistence

#### desktop-tabs.json

The tab layout is persisted to `<configDir>/desktop-tabs.json`:

```json
{
  "tabs": [
    {
      "id": "abc123",
      "scope": "project",
      "workspaceRoot": "/home/user/my-project",
      "topicId": "topic-1",
      "model": "deepseek/deepseek-reasoner",
      "effort": "high",
      "mode": "normal"
    }
  ],
  "activeTab": "abc123"
}
```

The file is written atomically (tmpfile + rename) after every tab operation (open, close, reorder, activate). On startup, the application reads this file and restores the tab layout, rebuilding each tab's controller in background goroutines.

#### desktop-projects.json

The project registry is persisted to `<configDir>/desktop-projects.json`:

```json
{
  "globalTitle": "Global",
  "globalColor": "purple",
  "globalTopics": ["topic-1", "topic-2"],
  "projects": [
    {
      "root": "/home/user/backend",
      "title": "Backend Service",
      "color": "blue",
      "topics": ["auth-feature", "api-refactor"]
    }
  ]
}
```

Projects are deduplicated by normalized root path. If the same root appears multiple times (e.g., from manual edits), the entries are merged: titles and colors from later entries fill in blanks, and topic lists are unioned.

### Tab Operations

#### OpenProjectTab

`OpenProjectTab(workspaceRoot, topicID)` creates a new project-scoped tab:

1. Normalizes the workspace root to an absolute path.
2. Checks if a tab with the same `(workspaceRoot, topicID)` already exists — if so, activates the existing tab instead of creating a duplicate.
3. Generates a unique tab ID and auto-titles the topic.
4. Creates the `WorkspaceTab` and its `tabEventSink`.
5. Registers the tab in the app's tab map and order list.
6. Saves the tab layout to disk.
7. Launches `buildTabController` in a background goroutine.

#### OpenGlobalTab

`OpenGlobalTab(topicID)` creates a new global-scoped tab:

1. Ensures the global workspace root directory exists.
2. Same deduplication, creation, and background build process as `OpenProjectTab`.

#### SetActiveTab

`SetActiveTab(tabID)` switches the frontend's active tab. A no-op when the tab is already active or the ID is unknown. Persists the active tab to disk.

#### ReorderTabs

`ReorderTabs(tabIDs)` persists the frontend's manual tab order. Validates that the submitted order contains every currently open tab exactly once (no duplicates, no missing tabs, no extra tabs).

#### CloseTab

`CloseTab(tabID)` shuts down and removes a tab:

1. **Cannot close the last tab**: The application always maintains at least one tab. The frontend should prompt the user before attempting to close the last tab.
2. Removes the tab from the map and order list.
3. If the closed tab was active, auto-activates the adjacent tab (using the closed tab's index in the order, clamped to valid bounds).
4. Tears down the controller outside the lock: cancels in-flight work, takes a final snapshot, and closes the controller.
5. Nullifies the sink's context to prevent further event emissions.

### buildTabController

`buildTabController(tab)` assembles a controller for a tab in a background goroutine:

1. Loads the workspace-specific configuration via `config.LoadForRoot(root)`.
2. **Promotes provider keys to credentials**: Calls `promoteProviderKeysToCredentials(cfg)` to lift project-scoped API keys into the global credentials store. This means a key resolved from a project's `.env` file becomes available in every other workspace, avoiding redundant configuration.
3. Resolves the model reference from the tab's stored model or the configuration default.
4. Builds the controller via `boot.Build` with the resolved options, including the tab's event sink and effort override.
5. Enables interactive approval for the controller.
6. Applies the tab's saved mode (normal/plan).
7. Resolves or creates a session path, restoring an existing session if the topic has one.
8. Persists scope and topic metadata to the session's branch metadata.
9. Loads existing telemetry if resuming a session.
10. Sets the controller on the tab and marks it as ready.
11. Emits the `agent:ready` event to the frontend.

If any step fails, the error is stored in `tab.StartupErr` and the tab is marked as ready (so the frontend can display the error), but the controller remains nil.

## Desktop Auto-Updater

**Source:** `desktop/updater.go`, `desktop/internal/update/manifest.go`, `desktop/internal/update/verify.go`

### Overview

The desktop application includes an auto-updater that checks for new versions, downloads signed artifacts, verifies their authenticity, and applies the update in place (on Windows and Linux) or directs the user to a manual download (on macOS). The updater is designed to be secure, reliable, and transparent — every update is verified with minisign signatures before it touches disk.

### Manifest: latest.json

The `Manifest` struct represents the `latest.json` file published alongside each desktop release:

| Field | Type | Description |
|---|---|---|
| `Version` | `string` | Release version (e.g., `"v1.1.0"`). |
| `Notes` | `string` | Markdown release notes. |
| `PubDate` | `string` | RFC3339 publication date (optional). |
| `DownloadPage` | `string` | Human-facing download page URL (macOS manual-update fallback). |
| `Platforms` | `map[string]Asset` | Per-platform artifacts, keyed by `PlatformKey` (e.g., `"darwin-arm64"`). |

### Asset

Each platform entry in the manifest includes:

| Field | Type | Description |
|---|---|---|
| `URL` | `string` | Direct download URL for the artifact. |
| `Sig` | `string` | URL of the detached minisign signature (`.minisig` file). |
| `Size` | `int64` | Artifact size in bytes (for download progress denominator). |
| `SHA256` | `string` | Lowercase hex digest for a second integrity check. |

### PlatformKey

`PlatformKey(goos, goarch)` constructs the manifest lookup key as `"<goos>-<goarch>"` (e.g., `"darwin-arm64"`, `"windows-amd64"`, `"linux-amd64"`). `CurrentPlatform()` returns the key for the running binary.

### Dual-Endpoint Fetch

`fetchManifest(ctx, c)` fetches the manifest from two endpoints in order:

1. **R2 mirror** (primary): `https://pub-147fb53b9c1e4bbf891a257968619ea7.r2.dev/latest/latest.json` — fast, especially in China where GitHub is often slow or blocked.
2. **GitHub releases** (fallback): `https://github.com/esengine/reasonix/releases/latest/download/latest.json` — reliable when R2 is unavailable.

If the primary endpoint succeeds, the fallback is not tried. If both fail, the last error is returned.

### Version Comparison

`evaluate(current, m)` compares the running version against the manifest:

1. Normalizes both versions to semver format (`vX.Y.Z`) via `normalizeVersion`.
2. Dev builds (version `"dev"` or invalid semver) never auto-prompt for updates.
3. If the latest version is semver-greater than the current version, `Available` is set to true.
4. Populates `CanSelfUpdate` (true for Windows/Linux, false for macOS).
5. Sets `AssetSize` from the manifest for the progress bar.

### Minisign Signature Verification

`Verify(data, sig)` checks the artifact's authenticity using the embedded minisign public key (Key ID `AF12CA46F4A9EBB0`). The verification process:

1. Parses the embedded public key text into a `minisign.PublicKey`.
2. Calls `minisign.Verify(key, data, sig)` to validate the signature.
3. Returns nil on success (artifact is authentic) or an error on failure (do not trust the artifact).

The public key is safe to embed in the binary — only the private half (stored in CI secrets) can produce valid signatures. If the signing key is ever rotated, both the embedded public key and the CI secret must be updated in lockstep.

For testability, the core logic lives in `verifyWith(pubText, data, sig)`, which accepts an arbitrary public key text. This allows tests to use throwaway key pairs without requiring the embedded key's secret counterpart.

### SHA-256 Integrity Check

After signature verification, `checkSHA256(data, want)` verifies the artifact's SHA-256 digest matches the manifest's `sha256` field. This provides a second layer of integrity checking independent of the minisign signature.

### Download with Progress

`download(ctx, c, url, total, onProgress)` fetches an artifact into memory with progress reporting:

1. Issues an HTTP GET request with the configured proxy settings.
2. Overrides the expected total with `Content-Length` if available.
3. Wraps the response body in a `progressReader` that invokes `onProgress` approximately every 256 KiB.
4. Always emits a final progress event on `io.EOF`.

Progress events are throttled to avoid flooding the Wails event channel, which could cause UI jank.

### Platform-Specific Apply

#### Linux

`applyLinux(targz)` extracts the `reasonix-desktop` binary from the downloaded `.tar.gz` archive and applies it in place using `selfupdate.Apply`. The `selfupdate` library handles the complexity of replacing a running binary on Linux by writing the new binary to a temporary file and using `rename` to atomically swap it.

#### Windows

`applyWindows(installer)` writes the downloaded NSIS installer to a temporary file and launches it. The per-user installer needs no admin rights and its finish page relaunches the app. The installer targets the running app's own directory (via `currentInstallDir()`), ensuring the update overwrites in place rather than landing a second copy at the per-user default location.

#### macOS

macOS does not support in-place self-updates. Without a Developer ID signature and notarization, swapping the `.app` bundle and relaunching would trip Gatekeeper. Instead, the updater directs the user to the download page for a manual update.

### Relaunch

After a successful in-place update, `relaunch()` starts a fresh copy of the replaced executable. The current process then exits, allowing the new binary to take over. The new process inherits `stdout`, `stderr`, and `stdin` from the current process.

### UpdateInfo: Frontend Display

The `UpdateInfo` struct drives the frontend's update banner:

| Field | Type | Description |
|---|---|---|
| `Available` | `bool` | Whether an update is available. |
| `Current` | `string` | The currently running version. |
| `Latest` | `string` | The latest available version. |
| `Notes` | `string` | Markdown release notes. |
| `CanSelfUpdate` | `bool` | Whether in-place update is supported (false on macOS). |
| `DownloadURL` | `string` | URL for manual download (macOS path). |
| `AssetSize` | `int64` | Artifact size for the progress bar. |
| `Err` | `string` | Error message if the update check failed. |

### Security Model

The auto-updater follows a defense-in-depth approach:

1. **HTTPS**: All manifest and artifact downloads use HTTPS.
2. **Dual-source**: The R2 mirror and GitHub releases provide redundancy.
3. **Minisign verification**: Every artifact is verified against the embedded public key before it touches disk.
4. **SHA-256 check**: A second integrity check independent of the signature.
5. **Proxy support**: The updater respects the user's configured network proxy.
6. **No unsigned execution**: The updater never applies an update whose signature hasn't been verified.
